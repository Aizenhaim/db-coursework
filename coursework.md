## ВВЕДЕНИЕ

Гражданская авиация является одной из наиболее динамично развивающихся отраслей мировой экономики. По данным Международной ассоциации воздушного транспорта (IATA), ежегодный объём авиаперевозок в мире исчисляется миллиардами пассажиров, а рынок авиабилетов продолжает демонстрировать устойчивый рост даже в условиях геополитической нестабильности. В России, несмотря на ограничения последних лет, внутренний авиарынок сохраняет высокую активность: в 2023–2024 годах отечественные авиакомпании перевезли более 100 миллионов пассажиров, что подчёркивает стратегическую значимость отрасли.

Современные авиакомпании и агентства по продаже авиабилетов сталкиваются с необходимостью обрабатывать огромные массивы информации: данные о рейсах и маршрутах, сведения о пассажирах, тарифах, бронированиях и проданных билетах. Ручная обработка таких данных невозможна — она требует высокоэффективных автоматизированных информационных систем, в основе которых лежат реляционные базы данных. Корректно спроектированная база данных позволяет обеспечить целостность и непротиворечивость данных, высокую скорость обработки запросов, надёжность хранения и удобство сопровождения системы [2, 3].

Актуальность разработки базы данных учёта продаж авиабилетов обусловлена рядом факторов. Во-первых, авиабилетная система является одной из наиболее транзакционно нагруженных — продажа, бронирование, отмена и изменение билетов происходят параллельно в режиме реального времени. Во-вторых, информация о пассажирах, рейсах и оплате относится к персональным и финансовым данным, что предъявляет повышенные требования к целостности и безопасности хранения. В-третьих, разнообразие тарифов, классов обслуживания и маршрутов обусловливает сложную структуру данных, требующую грамотного реляционного проектирования.

**Объектом исследования** является деятельность авиакомпании (системы продажи авиабилетов) по реализации пассажирских авиаперевозок.

**Предметом исследования** выступают информационные процессы и структура данных, возникающие при учёте продаж авиабилетов: регистрация рейсов, бронирование и продажа билетов, управление тарифами, ведение реестра пассажиров.

**Цель курсовой работы** — спроектировать и реализовать реляционную базу данных для учёта продаж авиабилетов, охватывающую полный цикл от формирования рейса до продажи билета пассажиру.

Для достижения поставленной цели необходимо решить следующие **задачи**:

1. изучить предметную область и сформулировать требования к хранимым данным;
2. разработать концептуальную (инфологическую) ER-модель базы данных в EER-нотации;
3. обосновать выбор системы управления базами данных (СУБД);
4. выполнить преобразование концептуальной модели в даталогическую реляционную модель;
5. реализовать базу данных средствами выбранной СУБД: создать таблицы, заполнить тестовыми данными;
6. разработать SQL-запросы различных типов для извлечения аналитической информации;
7. реализовать триггеры и хранимые процедуры для автоматизации бизнес-логики.

В качестве **инструментального средства проектирования** используется MySQL Workbench — профессиональный инструмент для проектирования и администрирования баз данных MySQL, включающий встроенный редактор EER-диаграмм. Для ER-моделирования применяется EER-нотация (Enhanced Entity-Relationship), поддерживаемая MySQL Workbench и обеспечивающая наглядное отображение сущностей, атрибутов и связей реляционной модели данных.

В качестве **СУБД** выбрана MySQL 8.0 — свободно распространяемая реляционная СУБД с открытым исходным кодом, обеспечивающая высокую производительность, надёжность и соответствие стандарту SQL. Для работы с базой данных используется клиентское приложение MySQL Workbench.

**Структура работы.** Курсовая работа состоит из введения, двух глав, заключения, списка использованной литературы и двух приложений. В первой главе описывается предметная область, разрабатывается концептуальная и даталогическая модели базы данных, обосновывается выбор СУБД. Во второй главе описывается практическая реализация базы данных: создание объектов, заполнение данными, разработка запросов, триггеров и хранимых процедур.

## ГЛАВА 1. ПРОЕКТИРОВАНИЕ БАЗЫ ДАННЫХ

### 1.1 Описание предметной области

#### Характеристика предметной области

Предметная область данной работы — система учёта продаж авиабилетов крупной авиакомпании или авиакассы, реализующей билеты на рейсы нескольких перевозчиков. Система охватывает полный жизненный цикл авиабилета: от формирования рейса и назначения тарифов до бронирования, продажи и использования билета пассажиром.

Для целей данной работы рассматривается крупная авиакомпания, осуществляющая регулярные пассажирские перевозки. По масштабу деятельности такое предприятие соответствует крупному: численность персонала превышает 250 человек, годовой оборот — свыше 2 млрд рублей. В частности, «Аэрофлот» — крупнейшая российская авиакомпания — ежегодно перевозит более 40 миллионов пассажиров, располагает флотом из более чем 200 воздушных судов и выполняет рейсы в более чем 50 стран мира.

#### Требования к хранимым данным

Разрабатываемая база данных должна хранить следующие сведения:

**Об авиакомпаниях:** полное наименование авиакомпании, двухбуквенный код ИАТА, страна регистрации, контактный телефон, адрес электронной почты.

**Об аэропортах:** официальное наименование аэропорта, трёхбуквенный код ИАТА, город и страна расположения, часовой пояс (для корректного отображения времени вылета/прилёта).

**О воздушных судах (самолётах):** модель воздушного судна, государственный регистрационный номер, общее количество пассажирских мест, год выпуска, принадлежность авиакомпании.

**О маршрутах:** аэропорт вылета, аэропорт прилёта, расстояние между аэропортами в километрах, расчётная продолжительность полёта в минутах. Каждый маршрут определяется уникальной парой аэропортов.

**О классах обслуживания:** наименование класса (Эконом, Бизнес, Первый), норма бесплатного провоза багажа в килограммах, краткое описание условий.

**О рейсах:** номер рейса, маршрут, воздушное судно, авиакомпания-оператор, дата и время вылета, дата и время прилёта, текущий статус рейса (запланирован, задержан, отменён, выполнен).

**О тарифах:** каждый рейс предлагается в нескольких классах обслуживания с отдельной ценой и квотой мест. Для каждой комбинации рейс–класс хранится: цена билета, количество доступных мест, признак возвратности тарифа.

**О пассажирах:** фамилия, имя, отчество, серия и номер паспорта (уникальный идентификатор), дата рождения, гражданство, контактный телефон, адрес электронной почты.

**О билетах:** уникальный номер билета, пассажир, тариф (из которого определяется рейс и класс), номер места в самолёте, дата и время бронирования, текущий статус билета (забронирован, оплачен, отменён, использован), способ оплаты (банковская карта, наличные, онлайн-оплата).

#### Источники и приёмники информации

Разрабатываемая система учёта продаж авиабилетов взаимодействует с несколькими категориями источников и приёмников информации.

**Источники информации** — субъекты и системы, поставляющие данные в базу:

- **Кассир / агент по продаже билетов** — вводит данные о новых пассажирах (INSERT в таблицу PASSENGER), создаёт бронирования и оформляет продажу билетов (INSERT в TICKET);
- **Диспетчер авиакомпании** — вносит информацию о рейсах и маршрутах (INSERT/UPDATE в FLIGHT, ROUTE), изменяет статус рейса при задержке или отмене (UPDATE FLIGHT.status);
- **Система тарификации** — формирует тарифные планы: цены и квоты мест по классам для каждого рейса (INSERT в TARIFF);
- **Пассажир (через веб-интерфейс или кассу)** — инициирует бронирование, оплату или отмену билета (вызов хранимых процедур и UPDATE TICKET.status).

**Приёмники информации** — субъекты и системы, получающие данные из базы:

- **Пассажир** — получает информацию о наличии мест и стоимости рейсов (процедура `sp_flight_availability`), а также историю своих поездок (`sp_passenger_tickets`);
- **Руководство авиакомпании** — формирует аналитические отчёты о выручке, загрузке рейсов и востребованности направлений (запросы Г, Д раздела 2.3);
- **Служба регистрации на рейс** — считывает данные о билетах и статусах пассажиров для регистрации (представление `vw_ticket_details`);
- **Система мониторинга рейсов** — получает актуальные статусы рейсов и остатки мест (SELECT-запросы к таблицам FLIGHT и TARIFF).

#### Типичные информационные запросы

Наиболее часто выполняемые операции в разрабатываемой базе данных:

- поиск доступных рейсов по направлению и дате;
- просмотр информации о билетах конкретного пассажира;
- получение сведений об остатке мест по классам на конкретном рейсе;
- формирование отчётов о выручке по авиакомпаниям и направлениям;
- анализ загрузки рейсов и востребованности маршрутов;
- проверка статуса рейса и связанных билетов.

Основную долю операций (более 80%) составляют операции чтения (SELECT-запросы). Запросы на изменение данных (INSERT, UPDATE) выполняются реже — при бронировании, продаже или отмене билетов.

#### Оценка масштаба и объёма данных

Для крупной авиакомпании, выполняющей ежедневно 200–300 рейсов, оценим объём данных в ключевой таблице — **БИЛЕТ**:

- среднее количество рейсов в день: 250;
- средняя загрузка одного рейса: 150 пассажиров;
- расчётное количество билетов в год: 250 × 150 × 365 = **13 687 500 записей**;
- с учётом хранения истории за 5 лет: ~70 млн записей.

Оценим объём хранимых данных. Одна запись в таблице БИЛЕТ содержит числовые, символьные и временны́е поля суммарным объёмом не более 200 байт:

70 000 000 × 200 байт ≈ 14 000 000 000 байт ≈ **14 ГБ**.

Все остальные таблицы (пассажиры, рейсы, тарифы и т.д.) в совокупности займут не более 5–10 ГБ. Таким образом, **общий объём базы данных составит около 20–25 ГБ** — что соответствует диапазону «десятки гигабайт».

Количество записей в ключевых таблицах:
- БИЛЕТ: десятки миллионов записей;
- ПАССАЖИР: единицы–десятки миллионов записей;
- РЕЙС: сотни тысяч записей;
- ТАРИФ, МАРШРУТ, САМОЛЁТ, АЭРОПОРТ: тысячи записей.

Скорость поступления данных умеренная: в часы пиковой продажи — до 500–1000 транзакций в минуту (бронирований и оплат).

#### Обоснование выбора характеристик связей между сущностями

В разработанной концептуальной модели определены следующие связи:

**Связь «Эксплуатирует» (АВИАКОМПАНИЯ — САМОЛЁТ).** Мощность 1:N — одна авиакомпания эксплуатирует множество воздушных судов, каждое воздушное судно принадлежит ровно одной авиакомпании. Связь неидентифицирующая: сущность САМОЛЁТ имеет собственный первичный ключ (`aircraft_id`) и является «сильной» сущностью. На стороне САМОЛЁТА связь обязательная (самолёт не может существовать без авиакомпании), на стороне АВИАКОМПАНИИ — необязательная (новая авиакомпания может не иметь самолётов).

**Связь «Является аэропортом вылета» (АЭРОПОРТ — МАРШРУТ).** Мощность 1:N — из одного аэропорта могут отправляться рейсы по многим маршрутам. Связь неидентифицирующая, обязательная со стороны МАРШРУТА (маршрут не может существовать без аэропорта вылета), необязательная со стороны АЭРОПОРТА (аэропорт может не иметь исходящих маршрутов).

**Связь «Является аэропортом прилёта» (АЭРОПОРТ — МАРШРУТ).** Аналогична предыдущей связи, но определяет пункт назначения маршрута. Мощность 1:N, связь неидентифицирующая, обязательная со стороны МАРШРУТА, необязательная со стороны АЭРОПОРТА (аэропорт может не иметь входящих маршрутов).

**Связь «Выполняется по» (МАРШРУТ — РЕЙС).** Мощность 1:N — один маршрут может обслуживаться многими рейсами (например, ежедневными рейсами между Москвой и Санкт-Петербургом). Связь неидентифицирующая, обязательная со стороны РЕЙСА, необязательная со стороны МАРШРУТА.

**Связь «Выполняется на» (САМОЛЁТ — РЕЙС).** Мощность 1:N — один самолёт может быть назначен на несколько рейсов (в разные дни). Связь неидентифицирующая, обязательная со стороны РЕЙСА, необязательная со стороны САМОЛЁТА (воздушное судно может временно не эксплуатироваться).

**Связь «Оперирует» (АВИАКОМПАНИЯ — РЕЙС).** Мощность 1:N — одна авиакомпания выполняет множество рейсов, каждый рейс выполняется одной авиакомпанией. Связь неидентифицирующая, обязательная со стороны РЕЙСА, необязательная со стороны АВИАКОМПАНИИ (авиакомпания может не иметь запланированных рейсов).

**Связь «Включает тариф» (РЕЙС — ТАРИФ).** Мощность 1:N — для одного рейса определяется несколько тарифов (по числу классов обслуживания). Связь неидентифицирующая, обязательная со стороны ТАРИФА, необязательная со стороны РЕЙСА (рейс может быть создан без тарифов на этапе планирования).

**Связь «Применяется в» (КЛАСС ОБСЛУЖИВАНИЯ — ТАРИФ).** Мощность 1:N — один класс обслуживания применяется во многих тарифах (на разных рейсах). Связь неидентифицирующая, обязательная со стороны ТАРИФА, необязательная со стороны КЛАССА ОБСЛУЖИВАНИЯ (класс может существовать в справочнике без активных тарифов).

**Связь «Приобретает» (ПАССАЖИР — БИЛЕТ).** Мощность 1:N — один пассажир может иметь несколько билетов (на разные рейсы). Связь неидентифицирующая, обязательная со стороны БИЛЕТА (билет не может существовать без пассажира), необязательная со стороны ПАССАЖИРА.

**Связь «Реализуется в» (ТАРИФ — БИЛЕТ).** Мощность 1:N — по одному тарифу может быть продано несколько билетов (разным пассажирам). Связь неидентифицирующая, обязательная со стороны БИЛЕТА, необязательная со стороны ТАРИФА.

### 1.3 Обоснование выбора типа СУБД для хранения информации

#### Анализ характеристик предметной области

Для обоснованного выбора СУБД проведём оценку ключевых характеристик данных в разрабатываемой системе.

**Структура данных.** Предметная область «учёт продаж авиабилетов» предполагает хранение строго структурированных данных с фиксированными схемами [4]: реквизиты рейсов, пассажиров и билетов имеют постоянный и предсказуемый набор полей. Слабоструктурированные или неструктурированные данные (документы, изображения, произвольные JSON-объекты) в данной системе отсутствуют. Это является весомым аргументом в пользу реляционной модели данных.

**Объём данных.** Как было установлено в разделе 1.1, общий объём базы данных крупной авиакомпании составит около 20–25 ГБ, количество записей в ключевой таблице (БИЛЕТ) — десятки миллионов. Это соответствует диапазону «десятки гигабайт», в котором реляционные СУБД работают эффективно без необходимости перехода к распределённым NoSQL-решениям.

**Скорость поступления и изменения данных.** В пиковые периоды система обрабатывает до 500–1000 транзакций в минуту. Большинство операций — поисковые запросы на выборку (SELECT), не изменяющие данные. Операции записи (бронирование, продажа, отмена) значительно менее частотны. Такой профиль нагрузки типичен для реляционных OLTP-систем (Online Transaction Processing) [5].

**Требования к целостности данных (ACID).** Продажа авиабилета — транзакционная операция: при оплате одновременно должны быть уменьшено количество свободных мест в тарифе и создана запись о билете. Частичное выполнение операции недопустимо: нельзя принять деньги и не выдать билет, или выдать билет без уменьшения остатка мест. Следовательно, система предъявляет высокие требования к ACID-свойствам:

- **Атомарность** — вся транзакция (списание места + создание билета) выполняется либо целиком, либо не выполняется вовсе;
- **Согласованность** — база данных после каждой транзакции переходит из одного корректного состояния в другое;
- **Изоляция** — параллельные транзакции бронирования не видят незавершённых изменений друг друга, что предотвращает продажу одного места двум пассажирам;
- **Долговечность** — подтверждённая транзакция сохраняется даже в случае сбоя системы.

#### Обоснование выбора MySQL 8.0

С учётом проведённого анализа — сравнительно небольшого объёма данных (десятки гигабайт), жёсткой неизменяемой структуры, высоких требований к транзакционной целостности, преобладания операций чтения над записью — **для реализации базы данных выбрана реляционная СУБД MySQL 8.0**.

Аргументы в пользу данного выбора:

1. **Соответствие ACID.** Механизм хранения InnoDB (используемый по умолчанию в MySQL 8.x) обеспечивает полную поддержку транзакций, что критически важно для операций продажи билетов.

2. **Производительность.** MySQL 8.0 демонстрирует высокую скорость выполнения SELECT-запросов благодаря развитой системе индексирования (B-Tree, FULLTEXT, индексы на выражения). Для баз данных объёмом до сотен гигабайт производительность MySQL полностью удовлетворяет требованиям.

3. **Зрелость и надёжность.** MySQL является одной из наиболее распространённых СУБД в мире (по рейтингу DB-Engines входит в тройку лидеров [14]). Система эксплуатируется в высоконагруженных продакшн-средах крупных компаний (Facebook, Twitter, YouTube) на протяжении более 25 лет.

4. **Открытый исходный код.** MySQL распространяется под свободной лицензией GPL, что обеспечивает доступность без лицензионных затрат.

5. **Богатая экосистема.** Широкий выбор клиентских инструментов (MySQL Workbench, HeidiSQL, DBeaver, phpMyAdmin) упрощает разработку, администрирование и демонстрацию.

6. **Поддержка хранимых процедур, триггеров и представлений** — необходимых элементов данной курсовой работы.

Альтернативой мог бы выступить PostgreSQL — также реляционная СУБД с открытым кодом. PostgreSQL обладает более строгим соответствием стандарту SQL и более широкими возможностями для сложных аналитических запросов. Однако для данной задачи функциональность MySQL 8.0 является достаточной, а его более простая настройка и меньший порог вхождения делают его предпочтительным выбором. Применение NoSQL-решений (MongoDB, Cassandra) нецелесообразно ввиду строго структурированного характера данных и высоких требований к транзакционной целостности.

### 2.3 SQL-запросы. Команда SELECT

В данном разделе представлены SQL-запросы различных типов к разработанной базе данных. Каждый запрос сопровождается описанием семантики и SQL-кодом [6, 15].

#### Запрос А. Соединение таблиц через WHERE (соединение по равенству)

**Семантика запроса.** Данный запрос извлекает полный список проданных и забронированных (не отменённых) авиабилетов с указанием фамилии и имени пассажира, номера рейса, маршрута (в формате «код аэропорта вылета → код аэропорта прилёта»), класса обслуживания, цены билета и его текущего статуса. Запрос реализует соединение семи таблиц через условия равенства в предложении WHERE. Результат упорядочен по дате бронирования.

```sql
SELECT
    t.ticket_number                                         AS 'Номер билета',
    CONCAT(p.last_name, ' ', p.first_name)                 AS 'Пассажир',
    f.flight_number                                         AS 'Рейс',
    CONCAT(ap_dep.iata_code, ' → ', ap_arr.iata_code)      AS 'Маршрут',
    sc.class_name                                           AS 'Класс',
    tr.price                                                AS 'Цена, руб.',
    t.status                                                AS 'Статус'
FROM ticket t, passenger p, tariff tr, flight f,
     route r, airport ap_dep, airport ap_arr, service_class sc
WHERE t.passenger_id         = p.passenger_id
  AND t.tariff_id            = tr.tariff_id
  AND tr.flight_id           = f.flight_id
  AND tr.class_id            = sc.class_id
  AND f.route_id             = r.route_id
  AND r.departure_airport_id = ap_dep.airport_id
  AND r.arrival_airport_id   = ap_arr.airport_id
  AND t.status != 'cancelled'
ORDER BY t.booking_datetime;
```

#### Запрос Б. Соединение таблиц через INNER JOIN

**Семантика запроса.** Данный запрос идентичен по семантике запросу А — выводит список не отменённых билетов с детальной информацией о пассажире, рейсе и классе обслуживания. Отличие состоит в синтаксисе: соединение реализовано с использованием явного оператора INNER JOIN, что является предпочтительным современным стилем написания SQL-запросов и улучшает читаемость кода.

```sql
SELECT
    t.ticket_number                                         AS 'Номер билета',
    CONCAT(p.last_name, ' ', p.first_name)                 AS 'Пассажир',
    f.flight_number                                         AS 'Рейс',
    CONCAT(ap_dep.iata_code, ' → ', ap_arr.iata_code)      AS 'Маршрут',
    sc.class_name                                           AS 'Класс',
    tr.price                                                AS 'Цена, руб.',
    t.status                                                AS 'Статус'
FROM ticket t
INNER JOIN passenger    p       ON t.passenger_id           = p.passenger_id
INNER JOIN tariff       tr      ON t.tariff_id              = tr.tariff_id
INNER JOIN service_class sc     ON tr.class_id              = sc.class_id
INNER JOIN flight       f       ON tr.flight_id             = f.flight_id
INNER JOIN route        r       ON f.route_id               = r.route_id
INNER JOIN airport      ap_dep  ON r.departure_airport_id   = ap_dep.airport_id
INNER JOIN airport      ap_arr  ON r.arrival_airport_id     = ap_arr.airport_id
WHERE t.status != 'cancelled'
ORDER BY t.booking_datetime;
```

#### Запрос В. Использование процедурных возможностей SQL — команда CASE

**Семантика запроса.** Данный запрос извлекает список всех рейсов с их маршрутами, авиакомпаниями, расстоянием и датой вылета. Оператор CASE используется для категоризации рейсов по дальности: рейсы с расстоянием до 1000 км классифицируются как «Ближний», от 1000 до 3000 км — как «Средний», свыше 3000 км — как «Дальний». Такая категоризация полезна для анализа маршрутной сети и установления ценовой политики.

```sql
SELECT
    f.flight_number                                         AS 'Рейс',

    CASE
        WHEN r.distance_km < 1000  THEN 'Ближний'
        WHEN r.distance_km < 3000  THEN 'Средний'
        ELSE                            'Дальний'
    END                                                     AS 'Категория',
    f.departure_datetime                                    AS 'Вылет',
    f.status                                                AS 'Статус рейса'
FROM flight f
INNER JOIN route   r      ON f.route_id               = r.route_id
INNER JOIN airport ap_dep ON r.departure_airport_id   = ap_dep.airport_id
INNER JOIN airport ap_arr ON r.arrival_airport_id     = ap_arr.airport_id
INNER JOIN airline al     ON f.airline_id             = al.airline_id
ORDER BY r.distance_km;
```

#### Запрос Г. Группировки, группировочные функции и условие HAVING

**Семантика запроса.** Данный запрос вычисляет суммарную выручку по каждой авиакомпании от продажи оплаченных и использованных билетов, а также дополнительные показатели: количество проданных билетов, среднюю, минимальную и максимальную цену. Условие HAVING фильтрует результаты, оставляя только те авиакомпании, суммарная выручка которых превышает 50 000 рублей. Результат упорядочен по убыванию выручки.

```sql
SELECT
    al.name                                                 AS 'Авиакомпания',
    COUNT(t.ticket_id)                                      AS 'Кол-во билетов',
    SUM(tr.price)                                           AS 'Суммарная выручка, руб.',
    ROUND(AVG(tr.price), 2)                                 AS 'Средняя цена, руб.',
    MIN(tr.price)                                           AS 'Мин. цена, руб.',
    MAX(tr.price)                                           AS 'Макс. цена, руб.'
FROM ticket t
INNER JOIN tariff  tr  ON t.tariff_id  = tr.tariff_id
INNER JOIN flight  f   ON tr.flight_id = f.flight_id
INNER JOIN airline al  ON f.airline_id = al.airline_id
WHERE t.status IN ('paid', 'used')
GROUP BY al.airline_id, al.name
HAVING SUM(tr.price) > 50000
ORDER BY SUM(tr.price) DESC;
```

#### Запрос Д. Левое соединение (LEFT JOIN)

**Семантика запроса.** Данный запрос выводит все рейсы из базы данных с указанием количества проданных (не отменённых) билетов на каждый из них. Ключевая особенность — использование LEFT JOIN позволяет включить в результат рейсы, на которые ещё не продано ни одного билета (количество билетов для таких рейсов будет равно нулю). Запрос полезен для оперативного мониторинга загрузки рейсов.

```sql
SELECT
    f.flight_number                                         AS 'Рейс',
    CONCAT(ap_dep.iata_code, ' → ', ap_arr.iata_code)      AS 'Маршрут',
    f.departure_datetime                                    AS 'Дата вылета',
    f.status                                                AS 'Статус',
    COUNT(t.ticket_id)                                      AS 'Продано билетов'
FROM flight f
INNER JOIN route   r      ON f.route_id               = r.route_id
INNER JOIN airport ap_dep ON r.departure_airport_id   = ap_dep.airport_id
INNER JOIN airport ap_arr ON r.arrival_airport_id     = ap_arr.airport_id
LEFT  JOIN tariff  tr     ON tr.flight_id             = f.flight_id
LEFT  JOIN ticket  t      ON t.tariff_id              = tr.tariff_id
                          AND t.status != 'cancelled'
GROUP BY f.flight_id, f.flight_number, ap_dep.iata_code,
         ap_arr.iata_code, f.departure_datetime, f.status
ORDER BY f.departure_datetime;
```

#### Запрос Е. Вложенный подзапрос (вложенный SELECT)

**Семантика запроса.** Данный запрос находит пассажиров, которые приобрели билеты на рейсы с расстоянием маршрута выше среднего по всем маршрутам в базе данных. Во внешнем запросе выбираются уникальные данные пассажиров (ФИО и паспорт). Во внутреннем подзапросе определяется список идентификаторов пассажиров, имеющих активные билеты на дальние рейсы. Условие фильтрации — расстояние маршрута должно превышать среднее значение, вычисляемое вложенным агрегирующим подзапросом `SELECT AVG(distance_km) FROM route`.

```sql
SELECT DISTINCT
    CONCAT(p.last_name, ' ', p.first_name, ' ',
           COALESCE(p.middle_name,''))                      AS 'ФИО пассажира',
    p.passport_number                                       AS 'Паспорт',
    p.phone                                                 AS 'Телефон'
FROM passenger p
WHERE p.passenger_id IN (
    SELECT DISTINCT t.passenger_id
    FROM ticket t
    INNER JOIN tariff  tr  ON t.tariff_id  = tr.tariff_id
    INNER JOIN flight  f   ON tr.flight_id = f.flight_id
    INNER JOIN route   r   ON f.route_id   = r.route_id
    WHERE r.distance_km > (SELECT AVG(distance_km) FROM route)
      AND t.status != 'cancelled'
)
ORDER BY 1;
```

#### Запрос Ж. Создание представления (VIEW)

**Семантика запроса.** Данный запрос создаёт представление `vw_ticket_details` — виртуальную таблицу, объединяющую сведения о билете, пассажире, рейсе, маршруте, авиакомпании и классе обслуживания. Представление инкапсулирует сложный многотабличный JOIN и позволяет обращаться к полной информации о билете с помощью простого запроса `SELECT * FROM vw_ticket_details`. Это значительно упрощает разработку клиентских приложений и исключает дублирование сложной логики соединения таблиц в нескольких местах.

```sql
CREATE OR REPLACE VIEW vw_ticket_details AS
SELECT
    t.ticket_number     AS ticket_number,
    t.status            AS ticket_status,
    t.booking_datetime  AS booking_datetime,
    t.seat_number       AS seat_number,
    t.payment_method    AS payment_method,
    CONCAT(p.last_name, ' ', p.first_name) AS passenger_name,
    p.passport_number   AS passport_number,
    f.flight_number     AS flight_number,
    al.name             AS airline_name,
    ap_dep.city         AS departure_city,
    ap_arr.city         AS arrival_city,
    ap_dep.iata_code    AS dep_iata,
    ap_arr.iata_code    AS arr_iata,
    f.departure_datetime AS departure_datetime,
    f.arrival_datetime  AS arrival_datetime,
    sc.class_name       AS service_class,
    tr.price            AS price
FROM ticket t
INNER JOIN passenger    p       ON t.passenger_id           = p.passenger_id
INNER JOIN tariff       tr      ON t.tariff_id              = tr.tariff_id
INNER JOIN service_class sc     ON tr.class_id              = sc.class_id
INNER JOIN flight       f       ON tr.flight_id             = f.flight_id
```

### 2.4 Триггеры

Триггер — это хранимая процедура специального вида, которая автоматически выполняется системой управления базами данных при наступлении определённого события — операции вставки (INSERT), обновления (UPDATE) или удаления (DELETE) записей в указанной таблице. Триггеры позволяют реализовать бизнес-логику непосредственно на уровне базы данных, что обеспечивает её целостность вне зависимости от клиентского приложения.

В MySQL различают триггеры типа BEFORE (выполняются до изменения данных) и AFTER (выполняются после). BEFORE-триггеры могут изменять значения NEW и отменять операцию через SIGNAL. AFTER-триггеры удобны для связанных обновлений других таблиц.

В курсовой работе разработаны два триггера к таблице TICKET.

#### Триггер 1 — trg_ticket_before_insert

**Текстовое описание.** Первый триггер срабатывает типа BEFORE INSERT на таблице `ticket`. При попытке добавить новый билет триггер проверяет наличие свободных мест по соответствующему тарифу (`available_seats > 0`). Если мест нет — генерируется исключение через SIGNAL SQLSTATE '45000' с пояснительным сообщением, и вставка отменяется. Если места есть — счётчик `available_seats` в таблице `tariff` уменьшается на 1. Таким образом, триггер автоматически поддерживает актуальность остатка мест и предотвращает овербукинг (продажу мест сверх квоты).

```sql
DELIMITER $$

CREATE TRIGGER trg_ticket_before_insert
BEFORE INSERT ON ticket
FOR EACH ROW
BEGIN
    DECLARE v_available INT;

    SELECT available_seats
      INTO v_available
      FROM tariff
     WHERE tariff_id = NEW.tariff_id;

    IF NEW.status != 'cancelled' AND v_available <= 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Нет свободных мест в выбранном классе на данный рейс';
    END IF;

    IF NEW.status != 'cancelled' THEN
        UPDATE tariff
           SET available_seats = available_seats - 1
         WHERE tariff_id = NEW.tariff_id;
    END IF;
END$$

DELIMITER ;
```

#### Триггер 2 — trg_ticket_after_update

**Текстовое описание.** Второй триггер типа AFTER UPDATE на таблице `ticket` обрабатывает изменение статуса билета. Если статус билета изменяется с любого активного на `cancelled` (отмена) — триггер возвращает место обратно в тариф, увеличивая `available_seats` на 1. Если билет восстанавливается из отменённого состояния в активное — место снова занимается (счётчик уменьшается). Таким образом, количество свободных мест всегда актуально и соответствует реальному числу не отменённых билетов.

```sql
DELIMITER $$

CREATE TRIGGER trg_ticket_after_update
AFTER UPDATE ON ticket
FOR EACH ROW
BEGIN
    IF OLD.status != 'cancelled' AND NEW.status = 'cancelled' THEN
        UPDATE tariff
           SET available_seats = available_seats + 1
         WHERE tariff_id = NEW.tariff_id;
    END IF;

    IF OLD.status = 'cancelled' AND NEW.status != 'cancelled' THEN
        UPDATE tariff
           SET available_seats = available_seats - 1
         WHERE tariff_id = NEW.tariff_id;
    END IF;
END$$

DELIMITER ;
```

### 2.5 Хранимые процедуры

Хранимые процедуры — это именованные объекты базы данных, представляющие собой заранее скомпилированный набор SQL-инструкций, сохранённый на сервере и выполняемый по вызову клиентского приложения. В отличие от обычных SQL-запросов, хранимые процедуры могут содержать управляющие конструкции (IF, LOOP, WHILE), локальные переменные и параметры. Хранимые процедуры снижают нагрузку на сеть (передаётся только вызов, а не весь SQL-код), повышают безопасность (пользователи могут вызывать процедуру без прямого доступа к таблицам) и обеспечивают повторное использование кода.

В курсовой работе разработаны две хранимые процедуры.

#### Процедура 1 — sp_passenger_tickets

**Текстовое описание.** Процедура `sp_passenger_tickets` принимает один входной параметр — номер паспорта пассажира (`p_passport_number`). Процедура выполняет проверку существования пассажира с указанным паспортом: если пассажир не найден — возвращается информационное сообщение об ошибке. Если пассажир существует — возвращается полная история всех его билетов: номер билета, статус, номер рейса, авиакомпания, аэропорты вылета и прилёта, время вылета/прилёта, класс обслуживания, номер места, цена и способ оплаты. Результат упорядочен по дате бронирования в убывающем порядке (последние билеты — первыми). Процедура используется при регистрации пассажира на рейс, при обращении в службу поддержки, а также для формирования отчёта о поездках.

```sql
DELIMITER $$

CREATE PROCEDURE sp_passenger_tickets(IN p_passport_number VARCHAR(20))
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM passenger WHERE passport_number = p_passport_number
    ) THEN
        SELECT CONCAT('Пассажир с паспортом ',
                      p_passport_number, ' не найден') AS Сообщение;
    ELSE
        SELECT
            t.ticket_number                                     AS 'Номер билета',
            t.status                                            AS 'Статус',
            f.flight_number                                     AS 'Рейс',
            al.name                                             AS 'Авиакомпания',
            CONCAT(ap_dep.city, ' (', ap_dep.iata_code, ')')   AS 'Откуда',
            CONCAT(ap_arr.city, ' (', ap_arr.iata_code, ')')   AS 'Куда',
            f.departure_datetime                                AS 'Вылет',
            f.arrival_datetime                                  AS 'Прилёт',
            sc.class_name                                       AS 'Класс',
            t.seat_number                                       AS 'Место',
            tr.price                                            AS 'Цена, руб.',
            t.payment_method                                    AS 'Оплата',
            t.booking_datetime                                  AS 'Дата бронирования'
        FROM ticket t
        INNER JOIN passenger    p      ON t.passenger_id           = p.passenger_id
        INNER JOIN tariff       tr     ON t.tariff_id              = tr.tariff_id
        INNER JOIN service_class sc    ON tr.class_id              = sc.class_id
        INNER JOIN flight       f      ON tr.flight_id             = f.flight_id
        INNER JOIN airline      al     ON f.airline_id             = al.airline_id
        INNER JOIN route        r      ON f.route_id               = r.route_id
        INNER JOIN airport      ap_dep ON r.departure_airport_id   = ap_dep.airport_id
        INNER JOIN airport      ap_arr ON r.arrival_airport_id     = ap_arr.airport_id
        WHERE p.passport_number = p_passport_number
        ORDER BY t.booking_datetime DESC;
    END IF;
END$$

DELIMITER ;
```

#### Процедура 2 — sp_flight_availability

**Текстовое описание.** Процедура `sp_flight_availability` принимает два входных параметра: номер рейса (`p_flight_number`) и дату вылета (`p_flight_date`). По этим параметрам процедура находит рейс в базе данных и возвращает: общую информацию о рейсе (маршрут, статус) и детальную таблицу доступности мест по каждому классу обслуживания — с указанием цены, количества свободных мест, количества проданных билетов, типа тарифа (возвратный/невозвратный) и нормы багажа. Если рейс с указанными параметрами не найден — возвращается сообщение об ошибке. Процедура применяется при поиске и бронировании билетов через кассу или веб-интерфейс.

```sql
DELIMITER $$

CREATE PROCEDURE sp_flight_availability(
    IN p_flight_number VARCHAR(10),
    IN p_flight_date   DATE
)
BEGIN
    DECLARE v_flight_id   INT;
    DECLARE v_dep_city    VARCHAR(100);
    DECLARE v_arr_city    VARCHAR(100);
    DECLARE v_status      VARCHAR(20);

    SELECT f.flight_id, ap_dep.city, ap_arr.city, f.status
      INTO v_flight_id, v_dep_city, v_arr_city, v_status
    FROM flight f
    INNER JOIN route   r      ON f.route_id             = r.route_id
    INNER JOIN airport ap_dep ON r.departure_airport_id = ap_dep.airport_id
    INNER JOIN airport ap_arr ON r.arrival_airport_id   = ap_arr.airport_id
    WHERE f.flight_number = p_flight_number
      AND DATE(f.departure_datetime) = p_flight_date
    LIMIT 1;

    IF v_flight_id IS NULL THEN
        SELECT CONCAT('Рейс ', p_flight_number,
                      ' на ', p_flight_date, ' не найден') AS Сообщение;
    ELSE
        SELECT p_flight_number AS 'Рейс',
               CONCAT(v_dep_city, ' → ', v_arr_city) AS 'Маршрут',
               v_status AS 'Статус рейса';

        SELECT
            sc.class_name       AS 'Класс',
            tr.price            AS 'Цена, руб.',
            tr.available_seats  AS 'Свободных мест',
            (SELECT COUNT(*) FROM ticket tk
              WHERE tk.tariff_id = tr.tariff_id
                AND tk.status != 'cancelled') AS 'Продано билетов',
            CASE tr.is_refundable
                WHEN 1 THEN 'Возвратный'
                ELSE        'Невозвратный'
            END                 AS 'Тариф',
            sc.baggage_allowance_kg AS 'Багаж, кг'
        FROM tariff tr
        INNER JOIN service_class sc ON tr.class_id = sc.class_id
        WHERE tr.flight_id = v_flight_id
        ORDER BY tr.price;
    END IF;
END$$

DELIMITER ;
```

```sql
    airline_id   INT            NOT NULL AUTO_INCREMENT,
    name         VARCHAR(100)   NOT NULL,
    iata_code    CHAR(2)        NOT NULL,
    country      VARCHAR(50)    NOT NULL,
    phone        VARCHAR(20),
    email        VARCHAR(100),
    CONSTRAINT pk_airline      PRIMARY KEY (airline_id),
    CONSTRAINT uq_airline_iata UNIQUE (iata_code),
    CONSTRAINT ck_airline_email CHECK (email LIKE '%@%.%' OR email IS NULL)
);

CREATE TABLE airport (
    airport_id   INT            NOT NULL AUTO_INCREMENT,
    name         VARCHAR(150)   NOT NULL,
    iata_code    CHAR(3)        NOT NULL,
    city         VARCHAR(100)   NOT NULL,
    country      VARCHAR(50)    NOT NULL,
    timezone     VARCHAR(50)    NOT NULL,
    CONSTRAINT pk_airport      PRIMARY KEY (airport_id),
    CONSTRAINT uq_airport_iata UNIQUE (iata_code)
);

CREATE TABLE aircraft (
    aircraft_id         INT         NOT NULL AUTO_INCREMENT,
    model               VARCHAR(50) NOT NULL,
    registration_number VARCHAR(20) NOT NULL,
    total_seats         SMALLINT    NOT NULL,
    year_manufactured   YEAR,
    airline_id          INT         NOT NULL,
    CONSTRAINT pk_aircraft         PRIMARY KEY (aircraft_id),
    CONSTRAINT uq_aircraft_reg     UNIQUE (registration_number),
    CONSTRAINT fk_aircraft_airline FOREIGN KEY (airline_id) REFERENCES airline(airline_id),
    CONSTRAINT ck_aircraft_seats   CHECK (total_seats > 0)
);

CREATE TABLE route (
    route_id             INT  NOT NULL AUTO_INCREMENT,
    departure_airport_id INT  NOT NULL,
    arrival_airport_id   INT  NOT NULL,
    distance_km          INT,
    flight_duration_min  INT,
    CONSTRAINT pk_route           PRIMARY KEY (route_id),
    CONSTRAINT fk_route_departure FOREIGN KEY (departure_airport_id) REFERENCES airport(airport_id),
    CONSTRAINT fk_route_arrival   FOREIGN KEY (arrival_airport_id)   REFERENCES airport(airport_id),
    CONSTRAINT uq_route           UNIQUE (departure_airport_id, arrival_airport_id),
    CONSTRAINT ck_route_airports  CHECK (departure_airport_id <> arrival_airport_id),
    CONSTRAINT ck_route_distance  CHECK (distance_km > 0 OR distance_km IS NULL),
    CONSTRAINT ck_route_duration  CHECK (flight_duration_min > 0 OR flight_duration_min IS NULL)
);

CREATE TABLE service_class (
    class_id             INT          NOT NULL AUTO_INCREMENT,
    class_name           VARCHAR(50)  NOT NULL,
    baggage_allowance_kg TINYINT      NOT NULL DEFAULT 20,
    description          VARCHAR(200),
    CONSTRAINT pk_service_class       PRIMARY KEY (class_id),
    CONSTRAINT uq_service_class_name  UNIQUE (class_name),
    CONSTRAINT ck_service_baggage     CHECK (baggage_allowance_kg >= 0)
);

CREATE TABLE flight (
    flight_id          INT         NOT NULL AUTO_INCREMENT,
    flight_number      VARCHAR(10) NOT NULL,
    route_id           INT         NOT NULL,
    aircraft_id        INT         NOT NULL,
    airline_id         INT         NOT NULL,
    departure_datetime DATETIME    NOT NULL,
    arrival_datetime   DATETIME    NOT NULL,
    status ENUM('scheduled','delayed','cancelled','completed') NOT NULL DEFAULT 'scheduled',
    CONSTRAINT pk_flight          PRIMARY KEY (flight_id),
    CONSTRAINT fk_flight_route    FOREIGN KEY (route_id)    REFERENCES route(route_id),
    CONSTRAINT fk_flight_aircraft FOREIGN KEY (aircraft_id) REFERENCES aircraft(aircraft_id),
    CONSTRAINT fk_flight_airline  FOREIGN KEY (airline_id)  REFERENCES airline(airline_id),
    CONSTRAINT ck_flight_datetime CHECK (arrival_datetime > departure_datetime)
);

CREATE TABLE tariff (
    tariff_id       INT           NOT NULL AUTO_INCREMENT,
    flight_id       INT           NOT NULL,
    class_id        INT           NOT NULL,
    price           DECIMAL(10,2) NOT NULL,
    available_seats SMALLINT      NOT NULL,
    is_refundable   TINYINT(1)    NOT NULL DEFAULT 1,
    CONSTRAINT pk_tariff        PRIMARY KEY (tariff_id),
    CONSTRAINT fk_tariff_flight FOREIGN KEY (flight_id) REFERENCES flight(flight_id),
    CONSTRAINT fk_tariff_class  FOREIGN KEY (class_id)  REFERENCES service_class(class_id),
    CONSTRAINT uq_tariff        UNIQUE (flight_id, class_id),
    CONSTRAINT ck_tariff_price  CHECK (price > 0),
    CONSTRAINT ck_tariff_seats  CHECK (available_seats >= 0)
);

CREATE TABLE passenger (
    passenger_id    INT          NOT NULL AUTO_INCREMENT,
    last_name       VARCHAR(50)  NOT NULL,
    first_name      VARCHAR(50)  NOT NULL,
    middle_name     VARCHAR(50),
    passport_number VARCHAR(20)  NOT NULL,
    birth_date      DATE         NOT NULL,
    nationality     VARCHAR(50)  NOT NULL DEFAULT 'Россия',
    phone           VARCHAR(20),
    email           VARCHAR(100),
    CONSTRAINT pk_passenger          PRIMARY KEY (passenger_id),
    CONSTRAINT uq_passenger_passport UNIQUE (passport_number),
    CONSTRAINT ck_passenger_birth    CHECK (birth_date < CURDATE()),
    CONSTRAINT ck_passenger_email    CHECK (email LIKE '%@%.%' OR email IS NULL)
);

CREATE TABLE ticket (
    ticket_id       INT         NOT NULL AUTO_INCREMENT,
    ticket_number   VARCHAR(20) NOT NULL,
    passenger_id    INT         NOT NULL,
    tariff_id       INT         NOT NULL,
    seat_number     VARCHAR(5)  NOT NULL,
    booking_datetime DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status ENUM('booked','paid','cancelled','used') NOT NULL DEFAULT 'booked',
    payment_method ENUM('card','cash','online')    NOT NULL DEFAULT 'card',
    CONSTRAINT pk_ticket           PRIMARY KEY (ticket_id),
    CONSTRAINT uq_ticket_number    UNIQUE (ticket_number),
    CONSTRAINT fk_ticket_passenger FOREIGN KEY (passenger_id) REFERENCES passenger(passenger_id),
    CONSTRAINT fk_ticket_tariff    FOREIGN KEY (tariff_id)    REFERENCES tariff(tariff_id)
);
```
